> 作者：酷安@残話 · 模块内置完整使用说明与免责声明 · [GitHub](https://github.com/staciepomar-spec/RedGuo)

## 功能一览

### 一、状态栏

|------|------|

### 二、界面透明度（视频除外）

首页 / 二级播放页上**视频以外的所有浮层**（顶栏、右侧互动、标题、类型标签、热评、
选集条、进度条、全屏按钮……）统一乘一个系数。

生效值 = 宿主原值 × 界面透明度；命中槽位的单个组件再乘自己的透明度（层 × 单项）。

设置在**拖动时即写入配置**，重启红果、切页、新建视图都继续生效；
只有把滑杆拉回 100%，才还原成宿主原值（重置整个模块是另一件事，见「面板唤出与结构」）。

**为什么不会和宿主的淡入淡出打架**：写入方式是「宿主当前 alpha × 系数」，不是绝对值。
宿主把控制栏淡到 0，我们就写 0；它淡回 1，我们再乘 0.29 —— 该消失的浮层照样消失。

> **范围边界**：以视频容器（`id=i62`）为锚点，只在**页面根以内**收它的兄弟层。
> 所以页面外的背景图、底部标签栏（首页 / 剧场 / 我的）以及「领取」这类广告挂件
> 不在这个系数的作用范围里 —— 它们不浮在视频上，属于页面外的常驻元素。

**横屏默认不参与**：横屏是沉浸式观看场景，控件本来就少，整体压到 29% 会让画面像蒙了层灰。
需要的话在「界面显示 → 界面透明度」里打开「横屏也调节浮层透明度」。

**改动即时生效**，不需要重启。（改完立刻看到效果，也不影响正在播放的视频。）

> **关于「切视频时透明度会重新渲染一下」**：红果的播放页是 ViewPager + 每页一套 View 实例，
> 换一个视频就是**新建一棵视图树** —— 新视图的 alpha 默认是 1.0，必须由模块重新写上去。
> 也就是说「新视图必须被应用一次」这件事无法回避。
> 早期是等 1.2 秒一轮的周期循环兜底，于是新视频会先以不透明显示最多 1.2 秒，看着像闪一下。
> 现在改为**新视图一挂到窗口上就在下一个消息轮次内补一次应用**
> （hook `View.onAttachedToWindow`，并做合并 + 限流），闪一下从「最长 1.2 秒」压到「约 1 帧」。

> 顺带说明为什么**不能**做成「只在重启时应用一次」：那样只有启动时已存在的那批视图
> 会被应用，之后新建的每一页都永远不会应用 → 只有第一个视频生效，后面全部失效。

**可选：暂停时恢复组件原本透明度**（默认关闭，开关在本卡片内）。
开启后，二级播放页**暂停**时把这些 alpha 还原成宿主原值（方便看清界面），恢复播放后重新套用。
只影响透明度，不影响隐藏。暂停状态取自宿主 `TTVideoEngine.play()/pause()` 的调用事件。

### 六、底部导航栏 / 小白条隐藏

**开启后，只要在红果内，导航栏就全程不显示；退出红果（回到桌面或切到别的 App）才恢复。**

| 项 | 说明 |
|----|------|
| 开关 | 默认关闭（不填就保持宿主原样） |
| 生效范围 | 红果整个前台期间 —— 不止播放页，首页、剧场、商城等所有页面都隐藏 |
| 恢复时机 | 整个 App 退到后台时；App 内部切页面**不会**恢复 |

> 设计取舍：早期版本做过「静置 N 秒才隐藏、一碰就冒出来」，实测体验很差 ——
> 点个 tab、滑一下页面它就会弹回来，反复跳动反而比常显更烦。
> 因此改成**软件内常隐**，只保留「退出才恢复」这一个出口。

实现走系统 `WindowInsetsController`：`hide(WindowInsets.Type.navigationBars())` 收起，
`show(...)` 恢复，并设置 `BEHAVIOR_SHOW_TRANSIENT_BARS_BY_SWIPE`。

> **导航栏不是 DecorView 的子视图。** 实机 `dumpsys window` 显示它是
> `Window{... NavigationBar0}`，`pkg = com.android.systemui`，属于**跨进程独立窗口**
> （`ty = NAVIGATION_BAR`）。模块拿不到它的 View，`setVisibility` 一类做法必然无效，只能走系统 insets API。

需要留意的三点：

1. **单次 `hide()` 守不住。** 系统会在下拉通知栏、输入法弹出、Activity 切换等时机强制恢复导航栏，
   所以复用既有的 1.2s 重应用循环**周期性地重新 hide**（`hide()` 幂等，重复调用无副作用）。
2. **隐藏后 insets 会归零**，此时 `isVisible(navigationBars())` 反而报 `true`。
   所以用一份 `NAV_HIDDEN_MARK` 记录「确实由我们隐藏」的状态作为第一判据，
   insets 只作兜底 —— 否则会陷入每轮循环重复 `hide()` 的死循环。
3. **前台计数区分「内部切页」与「真的退出」**：`onStop` 里递减计数器，
   只有归零（整个 App 离开前台）才恢复导航栏，避免 App 内切 Activity 时误恢复。

面板里带一行诊断信息，显示导航栏高度、当前可见状态、是否已被本模块接管，以及
系统导航模式（手势 / 三键）。

### 七、播放器：画质 / 倍速 / 定时关闭关屏

| 功能 | 挂载点 |
|------|--------|
| 默认最高画质 | `TTVideoEngineImpl.configResolution(Resolution)` → 替换为 `ExtremelyHigh` |
| 自定义倍速 1.0~2.0x 无级（0.1 步进） | `PlaybackParams.setSpeed(F)` |
| 长按边缘临时倍速 1.0~2.0x（默认 2.0x） | 同上，按调用栈识别长按通路后改写 |
| **定时关闭到点直接熄屏** | `yr4.l.<init>`（宿主 `ScheduledStopPlayController` 的归零事件） |

改动对**下一个起播的视频**生效（自动连播即可见效）。

**倍速上限 2.0x（v2.80 修正）**：常规倍速与长按倍速**是同一条通路**——
两者最终都汇到 `PlaybackParams.setSpeed` → `TTPlayer._setFloatValue(0x3C)` 的 JNI
（v2.79 全链路逆向定案）。native 引擎允许的档位只有 `{1.0, 1.25, 1.5, 2.0}`，
超范围一律降档：用交替截帧差分实测，官方面板的 3.0x 三组meanDiff 42.5~47.1，
与 1.5x 理论值 46.1 吻合，即**实际只有 ≈1.5x**，2.0x 才是真2.0x。

因此 v2.80 起常规倍速也从「1.0~4.0x」收紧为 **1.0~2.0x**（`Config.speedCustom`
读/写侧钳制，历史已存的大值自动压回）。此前 UI 承诺了引擎做不到的范围——与
v2.42~2.68 长按侧犯的是同一个错。

> **关于「别的模块能做到 3x」**：火山引擎官方文档里确实有高倍速开关 ——
> 要 >3x 必须在 play/prepare 之前 `setIntOption(PLAYER_OPTION_ENABLE_PLAY_SPEED_EXTEND, 1)`。
> 但红果这个包内嵌的 SDK **没有这个常量**（26 个 dex 全量字符串检索为零），
> 所以这条路在当前版本走不通。市面上的红果模块（如红果综合模块）也是把
> 3.0 写进 UI、最终调用 `setPlaySpeed(300)` / `setSpeed(3.0f)` —— 与我们
> 第 154 行描述的是同一条通路，没有任何 native 侧绕过代码；按引擎的档位表，
> 它同样只会落到 1.5x。也就是说：**这个问题目前没有现成方案，不是我们没找到**。

**长按倍速**：在画面边缘长按会临时提速，松手回到常规倍速。宿主把提速峰值**硬编码为 2.0x**，
模块按调用来源识别出这条通路后把它改写成你设置的倍率；默认 2.0x 即等于宿主原行为。
松手回落也会被改写成你的常规倍速（否则会被宿主的基准 1.0x 冲掉）。

#### 定时关闭 → 直接关屏

官方「定时关闭」（播放页更多菜单 / feed 长按菜单里的那一项）到点只做两件事：
**停播** + `decorView.setKeepScreenOn(false)`。放开常亮之后屏幕并不会立刻黑，
要等系统的息屏超时（实测小米 15 上是 60 秒；若开了「充电时保持唤醒」甚至一直不灭）。

模块在**倒计时归零那一刻**用 root 注入一次电源键，直接熄屏。

挂载点选的是 `yr4.l` 的构造函数：宿主到点时执行 `yr4.i.h.onNext(new yr4.l())`
（日志 `count down ! stop play`），而全 APK 只有这一处 `new Lyr4/l;` ——
挂在构造函数上就等于「定时关闭生效」这个事件，且不会在每秒 tick 上产生任何开销。

> ⚠️ **需要 root —— 但只给 ReadGuo，红果保持无 root**
>
> 熄屏只有三条路：`PowerManager.goToSleep()`（需系统签名权限）、
> `DevicePolicyManager.lockNow()`（需设备管理员）、注入电源键（需 `INJECT_EVENTS`），
> 普通应用一个都拿不到，只能用 `su`。而 root 授权是**按调用方 uid** 判的 ——
> 模块代码跑在红果进程里，直接 `su` 就等于要求给红果 root。
>
> 所以这里做成**两级**：
>
> 1. **宿主先自己 su 一次**（万一你哪天给红果也授了权，直接生效，不走下面）；
> 2. 失败则把请求写成触发文件 `files/rg_guard/off.<时间戳>.req`，
>    由 **ReadGuo 自己的 root 守护**用 inotify 收到后注入电源键 ——
>    于是**只需要给 ReadGuo 授予 root**。
>
> **守护怎么装**（一次性，脚本随模块提供在 `module/assets/rg_guard/`）：
>
> ```bash
> adb push module/assets/rg_guard/rg_screenoff.sh      /data/local/tmp/
> adb push module/assets/rg_guard/rg_screenoff_hook.sh /data/local/tmp/
> adb shell "su -c 'cp /data/local/tmp/rg_screenoff.sh /data/adb/service.d/; \
>   cp /data/local/tmp/rg_screenoff_hook.sh /data/adb/; \
>   chmod 755 /data/adb/service.d/rg_screenoff.sh /data/adb/rg_screenoff_hook.sh'"
> ```
>
> KernelSU 开机时会执行 `/data/adb/service.d/*.sh`，守护随之启动（一个 inotify
> 等待进程，闲置不轮询、不耗电）。**卸载**：删掉这两个文件 + 重启
> （`rm /data/adb/service.d/rg_screenoff.sh /data/adb/rg_screenoff_hook.sh`）。
>
> 诊断：ReadGuo 侧写 `/data/local/tmp/rg_screenoff.log`；红果侧还是 `rgtools_log.txt`
> （`sleep-timer: 已投递熄屏请求 -> rg_guard/off.xxx.req`）。
>
> **为什么不能直接跨进程调用**（2026-10-02 实测，四条通道全废）：Android 11+ 的
> **包可见性**让红果看不见 ReadGuo —— `ContentResolver.call` 报 `Unknown authority`、
> `bindService` 返回 false、显式广播投递不到、显式 `startActivity` 静默不起来。
> 红果清单里既没有指向 ReadGuo 的 `<queries>` 也没有 `QUERY_ALL_PACKAGES`，
> 而宿主 APK 改不了。让 ReadGuo 去匹配红果 `<queries>` 里已有的
> `VIEW + BROWSABLE + https` 签名做「对等暴露」也无效。
> 文件触发是唯一不需要改动系统的通道。
>
> 发键前守护会先看屏幕状态吗？—— 会：宿主在投递前已经查过
> `PowerManager.isInteractive()`，屏幕黑着就不投递（电源键是**切换**键，
> 盲发会把已熄屏的设备点亮）。

> 只对**倒计时类**选项生效（「30 分钟后」/ 自定义时长）；「播完本剧」不走倒计时，
> 因此不会触发熄屏。

### 八、手势

红果在横竖屏是**两套完全不同**的手势语义，实测如下：

| 方向 | 单击 | 双击 | 模块接管 |
|------|------|------|----------|
| 竖屏（信息流 / 半屏播放页） | 暂停 / 恢复 | 点赞（已被模块拦掉） | 双击 = 打开评论区 |
| 横屏全屏 | 切换控制栏显隐 | **暂停 / 恢复** | 可选：三击 = 打开评论区 |

> 注意：横屏**单击不是暂停**，只是切换控制栏显隐；横屏的暂停手势是**双击**。
> 横屏屏幕中央那个大 ▶/⏸ 图标是状态指示兼播放/暂停按钮（显示 ▶ 表示当前已暂停）。

#### ⚠️ 声明：横屏下「三击打开评论区」与「双击暂停」**无法同时生效**

这不是实现取舍，是**手势本身的包含关系决定的**，无法绕过：

> **三次连击 = （第一下 + 第二下），再加第三下。而「第一下 + 第二下」本身就是一次双击。**

因此只有两种可能，没有第三种：

| 选择 | 做法 | 结果 |
|------|------|------|
| **A. 保住双击暂停**（默认） | 点击全部放行给宿主，横屏不接管 | 双击暂停 ✓ ｜ 三击开评论区 ✗ |
| **B. 保住三击开评论区** | 连击整段吞掉，宿主收不到双击 | 三击开评论区 ✓ ｜ 双击暂停 ✗（三击里那次双击被吞掉，所以不会误暂停） |

所以横屏要么保持宿主原生手势，要么换成三击开评论区，**二选一**。
默认是 A（保持双击暂停）；想用三击开评论区，到面板「手势」卡片里打开
「横屏三击打开评论区」，**打开后横屏双击就不再暂停**。

（理论上还有第三种做法：吞掉全部连击后，若超时没等到第三击，就**补注入一次合成双击**
去触发宿主的暂停。但这样双击暂停会延迟约 350ms 才响应，手感明显变差，
且合成手势依赖宿主内部时序、跨版本易碎，故未采用。）

### 九、清屏省心

清屏状态下 **N 秒**（默认 10，可在面板调 3~60 秒）不碰屏幕，**自动收起其余控件只留视频**；
触摸立即恢复。仅二级播放页生效。

> 正确入口：长按视频 → 播放设置 → 清屏播放。（选集条右侧那个方块图标不是清屏。）

### 十、屏蔽更新

拦截「发现新版本」升级弹窗。挂载在升级弹窗的**唯一创建入口**
`UpdateManager.h()`（该方法内部走 `PopProxy.popup(...)` 真正弹出），
因此覆盖全部三条 UI 通路（Pop 处理器 / 升级状态回调 / 升级服务）。

默认**开启**，可在面板关掉。改动即时生效，不影响任何其他弹窗。

> 宿主自带的 `app_update_config_v733 → enableOfficialUpgrade=false` 也能关掉主动升级，
> 但那个判据只在「当前是非正式版本」的分支里才被读到（`versionCode % 100` 落在 32~63 之间），
> 改装版会绕过它，所以模块直接拦 `h()` 更彻底。

### 十二、去广告

| 开关 | 拦什么 | 拦在哪 |
|------|--------|--------|
| **拦截全部广告位** | 开屏 / 推荐流 / 短剧 banner / 暂停插播 / 横屏插入 / 评论区 / 进度条插入……以及**宿主以后新增的广告位** | `NsAdImpl.checkAdAvailable(pos, src)` 与其实现类恒返回 false，另加三道闸门（见下） |
| 拦截开屏广告 | 启动页 / 全屏广告 | `NsUtilsDependImpl.canShowScreenAd(Object)` 恒 false |
| 隐藏信息流广告 | 已经预插入视频流的广告队列 | `FeedDrawAdManager.getAd()` 恒 null + 两个请求入口空实现 |

**总闸的来历**：借鉴开源模块 [FanqieHook](https://github.com/afwfv/FanqieHook)（番茄/红果去广告）
的调用点分析结论 —— 红果主进程里所有广告位「现在能不能出广告」的判定，
**全部汇聚到 `checkAdAvailable(String position, String source)`** 一个方法：

```
NsAdImpl.checkAdAvailable(pos, src)  →  tc3.a.checkAdAvailable(pos, src)   // 薄委托
tc3.a.c(pos)   不带 source 的包装    →  checkAdAvailable(pos, null)
tc3.a.b(pos)   AB 实验表（335 指令）  →  只被 checkAdAvailable 调用
```

hook 这一处即可全拦，因此不需要维护「拦截名单」。另外四道闸门做纵深防御
（宿主有些路径在查可用性之前就自己过了总开关，或根本不查而是直接塞已缓存的广告对象）：

| 闸门 | 作用 |
|------|------|
| `SeriesPauseAdImpl.canShowPauseAd(...)` | 短剧暂停页插播 |
| `NsAdImpl.enableSeriesFeedTopViewAd()` | 单列短剧 TopView 广告总开关 |
| `NsAdImpl.checkCanShowTopViewInMainPage(...)` | 首页 TopView 广告 |

这四个类名都是**长名**，不像混淆短名那样每次发版换字母，是整套里最稳的一层。

> **代价（务必知悉）**：「拦截全部广告位」会让用户主动点的「看视频得金币 / 免广告 / 催更」
> 等激励入口失效 —— 那里已经没有广告可播。发奖由服务端校验，拦广告不会让金币白得。
> 只想拦被动广告、保留激励流程的话，把这一项关掉、只用下面两项即可。

日志里会按广告位记一行，如 `ad: position=creator_ad (passive)`，
`(passive)` 是被动位、`(reward)` 是用户主动的金币位、`(unnamed)` 是宿主新增的未知位。

> 本项只处理红果自身的广告位。若同时装了别的去广告模块（如 newhookvip），
> 两者作用点不同、可以共存；对比效果时建议先关掉对方，否则分不清是谁拦的。

### 十三、暗色模式

三档：**跟随系统 / 浅色 / 深色**。调用的是宿主自带的深色皮肤
（`SkinManager.changeSkinType(Skin.DARK)`），换的是整套夜间资源，不是给界面蒙一层灰。

宿主在 `initSKinMode()` 里会看自己的「跟随系统」开关：打开时**无视本地偏好**、
直接按系统深色与否给初值。所以模块不写 SharedPreferences（写了下一轮启动就被覆盖），
而是启动时 hook 一次 `initSKinMode`、之后每个 Activity `onResume` 校验一次，
与目标不一致才切 —— 一致时零反射开销。

### 十四、屏幕密度（DPI）

滑杆 250~720，最左为「跟随系统」。只改界面尺寸，视频画面（SurfaceView 输出）不受影响。

原理：Android 的 dp→px 全部走 `Resources.getDisplayMetrics().density`，该对象可变且被共享。
模块在 `Activity.onCreate` **执行前**改写它，保证布局 inflate 时就按新密度计算。
红果主体没有缓存 density 的工具类，直接改 DisplayMetrics 即可全局生效。

**松手即生效**：密度是在布局 measure 的时候就定死的，光改配置不会有任何视觉变化，
所以拖动松手后会「同步落盘 → 收起面板 → 重建当前 Activity」。
面板会自己关掉是正常的 —— 它挂在要重建的那个 Activity 上，跟着一起销毁才不会漏窗口。
配置用 `commit()` 落盘而非 `apply()`，否则进程被随手杀掉会丢掉这最后一个值。

### 十五、播放页福袋 / 禁用热更新 / 多渠道兼容

- **隐藏播放页福袋**：右侧那条竖排「领取」浮标。结构是
  `容器[135x261] > 背景图 + 图标 + Lottie + 文字「领取」`，整棵树里只有「领取」两个字是文案节点，
  所以按文案上溯到容器整体隐藏（`boxOf` 的高度上限与「无其他文案」守卫正好停在容器这一层，
  实测命中 `c42.e`）。与「组件显隐」里的「右侧『领取』挂件（福袋）」是同一个开关，两处等价。
- **禁用热更新**：宿主用字节 Reparo（`ReparoHotFixInitServiceImpl`）。
  `doInit` 直接短路 → SDK 不初始化、**本地已下发的旧补丁也不再加载**；
  `loadRemotePatch` 同时短路 → 不再请求新补丁。
  只拦一个都不彻底：只拦下载，旧补丁仍生效；只拦初始化，后续回调会 NPE。
- **渠道兼容**：作用域同时声明 `com.phoenix.read`（改版）、
  `com.phoenix.read.oversea.gp`（Google Play 版）、`com.dragon.read`（官方）。
  三者业务视图类同名（dex 交集 23 万类），只有按构建随机化的混淆短名不同，
  已按渠道各给候选（如定时关闭控制器 `yr4.l` / `vm4.l`、双击监听 `r65.o0` / `o15.o0`）。
  Play 版没有 Reparo，热更新项在该渠道自动记为 `n/a`。

### 配置怎么跨进程送过去的

模块 App 与红果是**两个 uid、两个私有目录**，两头都堵死：

- 模块 App 写不进 `/data/data/com.phoenix.read/shared_prefs/`（无权限）；
- 红果也读不到模块的 —— Android 11+ 包可见性让它连模块的存在都看不见，
  ContentProvider / bindService / 广播 / Activity 四条显式通道全被静默拦掉
  （v2.x 实测确认，见「定时关闭 → 直接关屏」）。

唯一**不需要 root、也不需要宿主配合**的通道是**公共存储**：

```
模块 App  ──写入──▶  /storage/emulated/0/Documents/RGTools/rg_cfg.json
红果      ──读取──◀  同一文件（Config.init 时一次）
```

- 模块 App 用 `MediaStore.Files + RELATIVE_PATH` 写入，**不需要任何存储权限**
  （v3.03 导出日志已验证过这条路）；同名文件先查后覆盖，不会堆出 `rg_cfg (1).json`。
- 红果声明了 `MANAGE_EXTERNAL_STORAGE`（短剧要存视频，用户本来就会授权），
  可以直接 `File` 读，读不到再退回 MediaStore 查询。
- 配置按 SharedPreferences 的三种类型分桶存 JSON（`b` / `i` / `s`），
  导入时按桶还原，`boolean / int / String` 的类型不会在往返中丢失。

代价是**改完要重启一次红果**（模块 App 里点「重启红果」即可），换来的是零权限零 root。

### 留在红果面板里的项

自定义隐藏清单、底部标签栏勾选、逐槽位透明度这三类仍只能在红果内设置 ——
它们要实时扫描宿主的视图树，本进程没有那个能力。

### v2.57 (versionCode 75)

- **修复**：首页双击打开评论区时，视频会被暂停，而且是**延迟暂停**

  早期竖屏会吞掉第二击，宿主只看到第一击、按「单击确认」把视频暂停，

### v2.56 (versionCode 74)

三项优化（2.55 为同一次改动的前一版）：

- **规则引擎合并为一次遍历**。此前每条规则各自遍历一遍全树
  （11 个槽位 × 2~3 条规则 ≈ 20~40 遍），是所有规则都是「按单个视图判定」的谓词，
  故可合并：先把规则解析成任务表，再**一次遍历**边访问边判定全部任务。
  语义保持不变（同一视图被多个槽位命中时仍是「任务表里靠后的后写生效」，
  与合并前逐槽位 put 的顺序一致）。同时做懒查询：只有当任务表里确实存在某类规则时
  才去取类名 / 文案 / 资源名。
  **实测单次应用 13~19ms → 6~7ms**；其中「写状态」那一遍遍历只占 0~1ms。
  已用固定操作序列比对 HIT/MISS 日志验证等价性（34 行中 33 行逐字相同，
  唯一差异是日志**取样**不同：同一槽位命中了多个视图时，记录的是「树序第一个命中」
  而非「第一条规则的第一个命中」，两者都是合法命中，见下）。
- **重应用循环改为全局单例、且只服务前台 Activity**。此前每个 Activity 各起一个
  1.2s 循环、各管自己那棵树，栈里的旧 Activity 会持续空跑全树遍历。
  现在只有前台页面会被应用；旧页面回到前台时走 `onResume` 重新应用，不依赖该循环兜底。
  **实测日志里「周期」计数从 3 秒 5~6 次降到 2~3 次**（正好等于 1.2s 一轮）。
- **删除面板上的「双击时吞掉第二次点击（避免误触点赞）」开关**。
  它早已失效：竖屏判据恒否所以不吞，横屏则无条件吞满整段（见 v2.47/v2.51 说明），
  怎么切都没有效果。现直接从面板与配置中移除，横屏吞点击不再依赖任何用户开关。

诊断日志同步扩充为 `apply cost Nms (其中写状态 Mms / 3s 内: 挂载触发 X 次 / 周期 Y 次)`。

### v2.54 (versionCode 72)

- **修复**：切换视频时透明度会「重新渲染一下」（新视频先以不透明显示一小段时间再被应用）。
  根因是重应用只有 1.2 秒一轮的周期循环兜底，而播放页每页都是新 inflate 的视图树，
  新视图最长要等一轮才轮到。现新增 `View.onAttachedToWindow` hook：
  新视图一挂上窗口就在**下一个消息轮次内补一次应用**（并做合并与限流，见下）。
  实测安静期（通常就是看完一段再切下一个）条件下会立即补应用，闪烁基本落在切页动画里。
- 单次全树应用实测约 **13~19ms**（≈1 帧），所以补应用做了两级限流：
  挂载密集期 60ms、平时 250ms，避免长列表滚动时持续全树遍历。
  另加诊断日志 `apply cost Nms (3s 内: 挂载触发 X 次 / 周期 Y 次)`（仅在确有补应用时输出）。
- 明确**不做**「改动需重启才生效」：新视图必须被应用一次，否则只有启动时的第一个视频生效。

### v2.51 (versionCode 69)

三个新功能（2.49/2.50 为同一次的中间构建）：

- **长按倍速可调**（面板「播放画质 / 倍速」）。宿主长按边缘的提速峰值是硬编码 2.0x，
  模块按调用来源（调用栈）识别长按通路后改写为你设置的倍率，默认 2.0x。
  同时把松手回落改写成你的常规倍速，避免被宿主基准 1.0x 冲掉。
  实现改用**长按状态机**（一次长按内首个写入 = 提速，值变化 = 回落）而非比较数值大小 ——
  后者在「常规倍速低于宿主基准」时（如常规 0.8x、回落 1.0x）会把回落误判成提速。
- **清屏自动隐藏秒数可调**（新卡片「清屏省心」，3~60 秒，默认 10）。
  此前是代码里的硬编码常量。
- **屏蔽更新弹窗**（新卡片「屏蔽更新」，默认开启）。挂在升级弹窗的唯一创建入口
  `UpdateManager.h()`，覆盖 Pop 处理器 / 升级状态回调 / 升级服务三条通路；
  四个调用点都忽略返回值（其一仅包进 `WeakReference`，null 合法），故直接返回 null 安全。
